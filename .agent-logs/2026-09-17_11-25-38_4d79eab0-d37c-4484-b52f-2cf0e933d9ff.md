# Architecture

```
frontend/  Next.js 15 App Router · TS · Tailwind · GSAP+ScrollTrigger · Auth0 SDK
backend/   Go 1.23 · gin · gorm · Postgres
  ├── cmd/api/              main.go
  ├── internal/controllers/ auth, generation, models, keys, assets
  ├── internal/models/      User, APIKey, Generation, Asset (gorm)
  ├── internal/provider/    Provider interface + one file per vendor + registry
  ├── internal/services/    job orchestration, polling worker
  └── pkg/                  httpx, cryptox (AES-GCM for BYOK), jwtx (Auth0 JWKS)
```

**Auth (point 3):** Auth0 handles login in Next.js; backend is stateless and validates the Auth0 JWT against JWKS. No sessions, no password storage.

**Provider pattern (point 5):** every model lives in a static catalogue with its params and capabilities. At boot the registry checks which credentials exist and marks each model `enabled` / `locked`. `GET /api/v1/models` returns the whole catalogue with status, so the frontend can render locked models as locked rather than hiding them — which is what makes the model wall a feature.

**BYOK (point 6):** user keys encrypted at rest with AES-GCM, decrypted per-request, never returned to the client. A user's own key unlocks a locked model for that user only.

**Point 7:** two workflows, `main` → prod only. Vercel deploy for frontend, Render deploy hook for backend, with `go vet` + `go test` + `tsc` gating both.

3. **The health check could pass against the old instance.** It only looked for `status: ok`. If a deploy silently did nothing, CI went green.

That last one now waits for the **exact version just shipped**:


## Release versioning

| Trigger | Result | Version |
|---|---|---|
| Push to `main` | deploys both | `main-<short-sha>` |
| Push `v*` tag | deploys both + GitHub Release | `v1.0.0` |

These never double-fire — a branch push doesn't match a tag filter. Render builds the image itself, so CI can't bake the version in; the workflow sets `APP_VERSION` on the service *before* triggering the deploy. The release publishes only after **both** deploys succeed, so a tag never points at something that didn't reach production.

## What I built

An S3 driver written against the **S3 API**, not one vendor's SDK — so Neon, R2, S3 and MinIO are the same five variables:

```

AWS_ENDPOINT_URL_S3      https://br-<branch>.storage.c-2.<region>.aws.neon.tech

AWS_SECRET_ACCESS_KEY    nsk_live_…
```

Two details from Neon's docs that would have cost you an afternoon:

- **Path-style addressing is required** (bucket in the path, not the hostname). Virtual-hosted style is unsupported.
- **Recent AWS SDKs attach a CRC32 checksum to every request** and several S3-compatible stores reject it. I set checksums to "when required" — the Go equivalent of the `requestChecksumCalculation: 'WHEN_REQUIRED'` their TypeScript example sets.

## How Sandbox Motion Pro works

It's a **fake provider that fakes nothing about the pipeline**. Your run is in the database:

```
mock/motion-pro | succeeded | mock_1789675459274_a6419f5b2415 | 21s | video | .../gtv-videos-bucket/sample/ForBig...
```

The trick is in the job handle. [`Submit`](backend/internal/provider/mock.go) does no work — it encodes a **finish time** into the external id:

```go
work := 14 * time.Second              // video
id := fmt.Sprintf("mock_%d_%s", time.Now().Add(work).UnixMilli(), seed)
```

`Poll` then just compares that timestamp to now, returning a progress percentage until it passes, then a result. Two consequences worth knowing:

- **No shared state.** Poll needs nothing but the id, so the worker can restart mid-job and still finish it — the same property a real provider gives you.
- **The result is deterministic.** The asset is picked by hashing `prompt + model id`, so the same prompt always returns the same clip.

The output is a **real public sample video** from Google's test bucket, not a generated one. `Motion Pro` differs from `Motion` only in its spec: 12 credits vs 5, a 21:9 default, 15-second option, and 2 reference-image slots.

The point is that everything *around* it is real — the queue, claiming, polling, asset rows, credit spend, refund-on-failure. Your run took 21s end to end and cost 12 credits, which is why your balance reads 88.

## Credit counters

Added to `users` as you asked — no ledger table:

| Column | Meaning |
|---|---|
| `credits` | balance (existing) |
| `credits_spent` | cumulative, lifetime |
| `credits_refunded` | cumulative, from failed jobs |

Both move **in the same `UPDATE` as the balance**, so a crash between two writes can't leave them disagreeing. A spend the balance can't cover still moves nothing at all — tested, including that case.

The studio's credits pill now shows the totals on hover.

**One honest caveat:** counters start at zero for you. AutoMigrate adds the columns with a default and can't reconstruct history that was never recorded — so your 12 already spent won't appear. Everything from your next generation will.

If per-generation accounting matters later, a ledger table is the right shape, and these two columns are exactly what it would be derived from. Restart the backend to pick up the columns.
