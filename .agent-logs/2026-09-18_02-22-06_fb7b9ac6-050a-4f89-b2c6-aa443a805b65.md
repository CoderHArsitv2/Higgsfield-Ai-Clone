Answering your question directly: **it wasn't working before — it was failing earlier in the flow, so it never got as far as the state check.** Before, `/auth/login` threw `Invalid URL` and 500'd immediately. Fixing that let logins actually start, which exposed the next bug down the chain.

## Why the state doesn't match

The state lives in an encrypted `__txn_<state>` cookie set by `/auth/login` and read back at `/auth/callback`. The SDK caps how many of those it keeps. From [transaction-store.js](frontend/node_modules/@auth0/nextjs-auth0/dist/server/transaction-store.js), when the cap is hit it evicts oldest-first, and its own warning names the cause:

> `This usually means many login flows were started but never completed (e.g. prefetches or abandoned logins)`

[AuthPanel.tsx](frontend/components/auth/AuthPanel.tsx) rendered every sign-in button with `next/link`. Next prefetches those hrefs on sight, so just *opening* `/login` fired real requests to `/auth/login` for Google, email, and every other provider — each one starting a login and banking a transaction cookie nobody completes. Your own production logs show it:

```
error ε GET /auth/login?returnTo=/studio&connection=google-oauth2&_rsc=utQopaZyVbfSG9h2
```

That `_rsc=` is the prefetch. By the time you clicked, enough abandoned transactions had piled up that eviction could discard the one you actually needed — so Auth0 redirects back with a state the server no longer recognises.

The file's own doc comment said "Every button is a plain link", and your logout links in [AppNav.tsx:72](frontend/components/studio/AppNav.tsx#L72) and [Nav.tsx:105](frontend/components/landing/Nav.tsx#L105) already use `<a>`. The login buttons were the odd ones out.
